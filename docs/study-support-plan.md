# StudySupport 学習復習アプリ計画

## 1. 目的

小学4年生の家庭学習を支援する、1日10分程度の復習アプリを作る。

苦手な分野を優先して出題し、間違えた内容を適切な間隔で繰り返すことで、無理なく基礎を定着させる。

## 2. 対象と前提

- 主な利用者：小学4年生
- 補助利用者：保護者
- 想定利用時間：1日10分程度
- 想定端末：横向きで使用するAndroidタブレット
- 基準端末：Xiaomi Pad 6
- 物理解像度：2,880×1,800、16:10、11インチ
- プロトタイプ基準：横向き1,440×900 CSS px相当で開始し、実機の表示倍率確認後に確定する
- 想定ブラウザ：Android版Google Chrome
- 対応画面：タブレットサイズの横向きに固定し、スマートフォンや縦向き表示には対応しない
- 提供形態：Chromeからホーム画面へインストールして使うPWA
- 初期版ではアカウントを作らず、家庭のXiaomi Pad 6を主端末として使う
- 学習記録、履修状態、カスタム問題、設定は端末内へ保存する
- 端末故障やブラウザデータ消去に備え、保護者がJSON形式でバックアップと復元を行えるようにする
- 氏名、学校名、生年月日、位置情報などの個人情報は保存しない

## 3. 教科の優先順位

初期の優先順位は次のとおりとする。

1. 漢字
2. 単位
3. 分数
4. 日本地図
5. 理科全般

「今日の復習」10問の初期出題比率は次を目安とし、実際の正答率に応じて自動調整する。

| 分野 | 初期比率 |
| --- | ---: |
| 漢字 | 40% |
| 単位 | 25% |
| 分数 | 15% |
| 日本地図 | 10% |
| 理科 | 10% |

## 4. 学習体験の基本方針

- アプリを開いたら、迷わず「今日の10問」を始められる
- 前回間違えた問題、忘れそうな問題、新しい問題の順に優先する
- 正解数だけでなく、「新しくできるようになったこと」を見せる
- 不正解を責める表現や、連続記録が途切れたことへの罰を設けない
- 問題は短くし、必要に応じて図や具体例を使う
- 一度の学習が長くなりすぎないよう、標準問題数を固定する
- 自由に教科を選べる練習モードも用意する

## 5. 漢字の学習計画

### 5.1 対象範囲

漢字は次の2学年分を対象とする。

- 小学3年生の配当漢字：既習内容の復習と穴の発見
- 小学4年生の配当漢字：現在の授業に合わせた定着

3年生の漢字を一律に最初からやり直すのではなく、短い診断を行い、定着している漢字は出題頻度を下げる。苦手な漢字、読み書きの混同、送り仮名の間違いなどを優先して復習する。

### 5.2 初回診断

- 3年生の漢字を複数グループに分け、1回10問程度で少しずつ診断する
- 1日ですべて診断せず、通常の復習に混ぜる
- 「読める」「書ける」を別々に判定する
- 正解しても迷った問題は、本人が「もう一度」にできる
- 診断結果から、漢字ごとの初期習熟度を設定する

### 5.3 問題形式

- 読み問題は選択式にせず、画面上の50音表からひらがなまたはカタカナを1文字ずつ入力して答える
- 読み問題では、濁音、半濁音、小さい「ゃ・ゅ・ょ・っ」、長音、文字削除を入力できるようにする
- 読み問題は単独の漢字だけでなく、文中や熟語中の読みも扱う
- 書き問題は、タブレット上の手書き入力エリアに指またはペンで書いて答える
- 書き問題では、字形だけでなく画数と書き順も判定する
- 文の空欄、熟語、同音異義語、送り仮名を含む問題を扱う
- 都道府県名に使われる漢字を、日本地図と関連付けて覚える

読みの回答は確定操作後に正誤判定する。書きの回答は一画ごとに入力を受け取り、画数、書き順、各画の大まかな形と位置を判定する。誤った場合はその場でやり直し、正解するまで通常の「次へ」は表示しない。

書き問題には「分からない」ボタンを設ける。押した場合は不正解として記録し、正しい書き順のアニメーションまたはガイドを確認した後、なぞり書きまたは再入力で正しく書けた時点で次へ進める。単なるスキップにはしない。

手書き判定には Hanzi Writer のクイズ機能と、日本語漢字用のストロークデータを利用する方針とする。Hanzi Writer は一画ごとの正誤、ミス、完了イベント、判定の許容度、逆向きの画を許可するかどうかを設定できる。日本語用データは初期検証で3年生・4年生漢字の網羅率、日本の学校で教える字形・書き順との一致、タブレット上の誤判定率を確認する。

候補となる日本語用データは AnimCJK 由来の `hanzi-writer-data-ja` または同等形式のデータとする。KanjiVG は日本語漢字の字形・画方向・書き順を持つため、正解表示や不足データの確認に利用できるが、それ自体は手書き採点ライブラリではない。ライセンス表示と再配布条件は採用前に確定する。

厳密な美文字判定ではなく、学習目的に必要な画数、書き順、始点・終点、画の方向、全体配置を許容幅付きで判定する。

### 5.4 漢字ごとに記録する内容

- 学年
- 読み
- 書き
- 送り仮名
- 使用例
- 正答回数と誤答回数
- 最終出題日
- 次回出題日
- 間違い方
- 習熟度
- 学習済みかどうか
- 標準問題かカスタム問題か

### 5.5 習っていない漢字の管理

- 3年生、4年生の漢字一覧を学年別に表示する
- 一覧内の漢字ごとに「習った／まだ習っていない」を切り替えられる
- 「まだ習っていない」に設定した漢字は、今日の復習、初回診断、自由練習の自動出題対象から除外する
- 「習った」に変更した漢字は未学習状態で出題候補に加える
- 一覧には「すべて」「習った」「まだ習っていない」の絞り込みを用意する
- 3年生の漢字は初期状態を「習った」、4年生の漢字は初期設定時にまとめて選択できるようにする
- 設定変更は既存の回答履歴を削除せず、出題対象だけを変更する

### 5.6 カスタム漢字問題

よく間違う読み書きの問題を保護者が追加、編集、削除できるようにする。

- 種別：読み問題または書き問題
- 出題文：対象の漢字や熟語を含む短い問題文
- 対象部分：回答させる漢字または読み
- 正解：読み、または書かせる漢字
- 補足：任意の短い説明や例文
- 有効／無効：削除せず一時的に出題対象外にできる

カスタム問題も標準問題と同じ習熟度・復習スケジュールで扱う。削除時は確認を表示する。削除した問題の回答履歴は集計から除外するが、誤操作に備えて内部では復元可能な論理削除を基本とする。

### 5.7 漢字問題の状態遷移

| 現在の状態 | 操作・判定 | 次の状態 | 記録 |
| --- | --- | --- | --- |
| 読みを入力中 | 50音表で入力 | 読みを入力中 | 未確定 |
| 読みを入力中 | 回答が正解 | 正解表示 | 正解 |
| 読みを入力中 | 回答が不正解 | 再入力 | 誤答1回を記録 |
| 書きを入力中 | 一画が妥当 | 次の画を入力 | 画数を進める |
| 書きを入力中 | 書き順や画が不正 | 同じ画から再入力 | 誤りを記録 |
| 書きを入力中 | 全画が正解 | 正解表示 | 正解。ただし途中の誤りも保持 |
| 書きを入力中 | 「分からない」 | 正解・書き順を確認 | 不正解 |
| 正解・書き順を確認 | ガイド後に正しく書く | 正解表示 | 補助あり完了 |
| 正解表示 | 「次へ」 | 次の問題 | 復習予定を更新 |

未習漢字に切り替えられた問題は出題候補から除外し、進行中の問題に対する設定変更は次の学習セッションから反映する。

## 6. 単位の学習計画

### 6.1 対象

- 長さ：mm、cm、m、km
- 重さ：g、kg、t
- かさ：mL、dL、L
- 時間：秒、分、時間
- 面積：cm²、m²、km²、a、ha

### 6.2 問題形式

- 単位変換
- 大小比較
- 適切な単位の選択
- 身近な物の量を予想する問題
- 短い文章題

ゼロの数だけを暗記する学習にせず、図や身近な物との比較によって量の感覚を身に付けられるようにする。

## 7. 分数の学習計画

次の順序で学習する。

1. 図を見て分数を答える
2. 数直線上の位置を選ぶ
3. 真分数、仮分数、帯分数を区別する
4. 仮分数と帯分数を相互に変換する
5. 大きさの等しい分数を見つける
6. 分数の大小を比較する
7. 同分母の分数を足し引きする

答えだけでなく、どこで考え方を間違えたかが分かる解説を用意する。

## 8. 日本地図の学習計画

- 地図上の位置から都道府県名を選ぶ
- 都道府県名から位置を選ぶ
- 地方別に練習する
- 都道府県の形から名前を当てる
- 間違えた都道府県だけを集中練習する
- 都道府県名に使われる漢字を漢字学習と連携させる

初期段階では県庁所在地や名産品まで広げず、名称、位置、地方区分、漢字を優先する。

## 9. 理科の学習計画

4年生の単元を中心に、短い図解カードを確認してから3問程度のクイズに進む構成とする。

- 空気と水の性質
- 金属、水、空気と温度
- 電流の働き
- 人の体のつくりと運動
- 季節と生物
- 雨水の行方と地面の様子
- 天気と気温
- 月と星

暗記問題だけでなく、実験結果の予想、観察結果の読み取り、理由の選択も扱う。

## 10. 復習スケジュール

問題または学習項目ごとに、習熟度を5段階で管理する。

| 状態 | 次回出題の目安 |
| --- | --- |
| 未学習 | 今日または近日 |
| 練習中 | 翌日 |
| もう少し | 3日後 |
| ほぼ定着 | 7日後 |
| 定着 | 30日後 |

不正解の場合は翌日を基本とする。正解でもヒントを使用した場合や本人が迷ったと申告した場合は、習熟度を大きく上げない。

### ホーム

### その他の問題画面

- ヒント

### 復習ボックス

### がんばり記録

### 保護者画面

### 漢字一覧・履修設定画面

## 12. データの基本単位

初期設計では、少なくとも次のデータを扱う。

- 問題
- 漢字や単元などの学習項目
- 回答履歴
- 項目ごとの習熟度
- 学習セッション
- 復習予定
- アプリ設定
- 漢字ごとの履修状態
- カスタム問題
- 手書きの一画ごとの入力と判定結果

問題文と正解だけでなく、対象学年、教科、単元、難易度、問題形式、解説、関連する学習項目を保持する。

### 12.1 端末内の保存単位

初期版ではすべての学習データをXiaomi Pad 6のブラウザ内に保存する。氏名やアカウントIDは持たず、この端末の1人分の学習データとして扱う。

- `kanjiStates`：習った／未習、読み・書きの習熟度、次回復習日
- `customQuestions`：保護者が登録した読み書き問題と有効状態
- `sessions`：学習開始・終了時刻、教科別問題数、完了状況
- `attempts`：問題、正誤、ミス回数、補助使用、回答時刻
- 生の手書き軌跡、筆圧、端末固有情報は保存しない

### 12.2 ローカル保存とバックアップ

- 回答確定時にIndexedDBへ即時保存する
- アプリ本体と教材をService Workerでキャッシュし、通信がなくても学習できるようにする
- 回答履歴は重複しないIDを持つ追記型データとする
- 習熟度は回答履歴から再計算可能にする
- 「習った／未習」とカスタム問題の編集は更新日時を持つ
- 学習途中でアプリを閉じても、確定済みの回答が失われないようにする
- 設定、履修状態、カスタム問題、学習履歴を1つのJSONファイルへ書き出し、同じアプリへ復元できるようにする
- バックアップ形式にはスキーマバージョンを含め、未知の形式や壊れたファイルを取り込まない

## 13. 開発ロードマップ

### フェーズ1：共通学習基盤と漢字

- ホーム、問題、結果画面
- タブレット横向き固定レイアウト
- 問題データの読み込み
- 正誤履歴と習熟度管理
- 復習スケジュール
- 3年生漢字の段階的診断
- 3年生、4年生の漢字問題
- 50音表による読み回答
- 漢字一覧と「習った／まだ習っていない」の管理
- 読み書きのカスタム問題管理
- IndexedDBへの進捗保存
- JSONバックアップと復元
- PWAとしてのインストールとオフライン利用

完了条件：毎日10問を解くことができ、読みを50音表で回答できる。未習漢字が出題されず、カスタム問題を登録・編集・無効化・削除でき、間違えた漢字が翌日以降に再出題される。

### フェーズ1.5：書き順付き手書き回答

- Hanzi Writer と日本語ストロークデータの技術検証
- 3年生・4年生漢字のデータ網羅率と日本字形の確認
- 判定の許容度と救済動作の定義
- 一画ごとの書き順、方向、位置判定
- 全画の字形判定
- 「分からない」から書き順確認、再練習への遷移
- 3年生、4年生の対象漢字データ整備

完了条件：対象漢字を正しい画数と書き順で入力した場合に完了でき、誤った画は再入力となる。「分からない」を押した場合は正解を確認し、正しく書き直した後に次へ進める。実機で子どもの正しい入力を不当に拒否しないことを確認する。

### フェーズ2：単位と分数

- 単位変換、量感、文章問題
- 分数の図と数直線
- 教科別、単元別の習熟度表示

完了条件：単位と分数を今日の復習に混ぜ、図付きの解説を確認できる。

### フェーズ3：日本地図

- 操作可能な日本地図
- 地方別練習
- 苦手な都道府県の集中復習
- 都道府県名と漢字問題の連携

完了条件：名称と位置を双方向で練習でき、間違えた都道府県が再出題される。

### フェーズ4：理科と保護者画面

- 単元別の図解カード
- 理科クイズ
- 保護者向け学習状況
- 出題比率の調整

完了条件：理科を含む全対象分野を今日の復習から学習できる。

### フェーズ5：試用と改善

実際に1〜2週間使用し、次を確認して改善する。

- 10分程度で終了できるか
- 説明なしで操作できるか
- 問題文が難しすぎないか
- 同じ問題が多すぎないか
- 本当に苦手な内容が優先されるか
- ごほうびや画面表現が年齢に合っているか

## 14. 検証方針

自動テストでは次を確認する。

- 正誤判定
- 単位変換
- 分数計算
- 習熟度の更新
- 次回復習日の決定
- 出題比率と問題数
- 同じ問題の過剰な連続出題の防止
- 学習記録の保存と復元
- アプリ終了後も確定済みの回答を復元できること
- JSONバックアップを作成し、初期化したテスト環境へ正しく復元できること
- 壊れたファイル、未知のバージョン、不正な項目を復元時に拒否すること
- 復元をキャンセルした場合に既存データが変化しないこと
- 未習漢字がすべての自動出題から除外されること
- 履修状態を変更しても過去の回答履歴が失われないこと
- 50音表の文字種、濁音、半濁音、小文字を含む正誤判定
- カスタム問題の登録、編集、無効化、論理削除
- 書き順、画数、画の方向が異なる入力の拒否
- 「分からない」後は再練習を完了するまで次へ進めないこと

実機確認では、子どもが迷わず操作できること、文字サイズ、50音表とボタンのタップ領域、手書き入力の追従性、正しい字の誤判定率、解説の分かりやすさ、1回の所要時間を確認する。手書き判定は自動テストの通過だけで完了とせず、実際に使用するタブレット上で保護者と子どもによる確認を必須とする。

## 15. プライバシーと安全性

初期版は子どもの氏名、学校名、生年月日などを収集せず、学習データをXiaomi Pad 6のブラウザ内だけに保存する。アプリの配信先へ学習履歴や手書きデータを送信しない。バックアップファイルは保護者が明示的に書き出し、安全な場所へ保管する。

| 操作 | 初期版での扱い |
| --- | --- |
| 問題を解く | 許可 |
| 学習履歴を端末内に保存 | 許可 |
| 学習履歴をクラウドへ同期 | 初期版では実施しない |
| 保護者が履歴を見る | この端末の保護者画面で許可 |
| 氏名、学校名などを入力する | 不要・保存しない |
| 生の手書き軌跡や筆圧を保存する | 実施しない |
| 保護者アカウントを作成する | 初期版では不要 |
| 子ども本人のアカウントを作成する | 実施しない |
| バックアップを書き出す、復元する | 保護者画面から確認後に実施 |
| 学習記録を削除する | 保護者画面から確認後に実施。実装後に人による確認を必須とする |

バックアップ復元と学習記録削除は既存データを置き換える高リスク機能として扱い、自動テストに加えて保護者による確認を必要とする。

### 15.1 初期版のアクセス方針

- 認証やログインは実装せず、家庭内のXiaomi Pad 6を信頼する単一端末モデルとする
- 保護者設定とカスタム問題管理には、簡単な保護者確認を追加する
- 端末を共有する人は学習履歴を閲覧できるため、端末自体の画面ロックを利用する
- バックアップファイルには学習履歴が含まれることを、書き出し前に保護者へ表示する

将来クラウド同期を追加する場合は、その時点で認証、所有権、アクセス制御、削除仕様を再設計し、人によるレビューを行う。

### 15.2 保存・復元時の不変条件

| 状況 | 必ず守ること |
| --- | --- |
| 回答保存中にアプリ終了 | 直前までの確定済み回答を壊さない |
| 同じ回答保存を再試行 | 同じ回答を二重計上しない |
| 未習設定を変更 | 過去履歴は保持し、以後の出題だけを止める |
| カスタム問題を削除 | 過去集計を壊さず、確認なしに削除しない |
| バックアップを復元 | 検証完了まで既存データを置き換えない |
| 復元が途中で失敗 | 既存データをそのまま保持する |
| 学習記録を初期化 | 対象を明示し、保護者の再確認後だけ実行する |

## 16. 技術方針（暫定）

- React
- TypeScript
- PWA
- IndexedDB：学習履歴、習熟度、履修状態、カスタム問題、設定の保存
- Service Worker：アプリ本体と教材のオフライン利用
- JSONエクスポート／インポート：手動バックアップと復元
- 静的ホスティング：アプリ本体の配信だけに使用し、学習データは送信しない
- Hanzi Writer：手書きクイズ、書き順判定、ヒント、書き順アニメーション
- 日本語ストロークデータ：AnimCJK由来の Hanzi Writer 互換データを第一候補とし、KanjiVGを検証用の参照候補とする
- タブレット横向き専用の固定レイアウト
- 対応する基準解像度を1つ決め、その画面内で学習操作を完結させる
- 縦向きでは回転案内のみを表示する
- 問題データは編集しやすい形式で管理する
- 学習中の進捗はブラウザ内へ保存し、オフラインでも利用できるようにする
- 生の手書き軌跡は判定中のみメモリ上で扱い、回答後は破棄する

技術構成は画面設計と問題データ設計を行った後に確定する。

### 16.1 デプロイ構成

```text
横向きタブレットのPWA
  ├─ GitHub Pages：画面、教材、漢字データをHTTPS配信
  ├─ Service Worker：必要なファイルを端末へキャッシュ
  ├─ IndexedDB：学習記録と設定を端末内へ保存
  └─ JSONファイル：保護者による手動バックアップと復元
```

配信先はGitHub Pagesとする。GitHub Actionsでテストと本番ビルドを行い、生成された `dist` だけをPagesへ渡す。初期ワークフローは手動実行に限定し、実際の公開は明示的な確認を取ってから行う。

### 16.2 採用候補の理由

- PWAの静的配信に適している
- GitHub上の問題JSONを編集するだけで問題パックを更新できる
- バックエンド、認証、データベースを運用せずに済む
- 学習データを家庭の端末外へ送らず、構成とプライバシー説明を単純にできる
- オフライン利用では配信先の障害や通信状態に影響されにくい
- 静的ファイルだけなので、将来ホスティング先を変更しやすい

将来、複数端末の共有、自動バックアップ、保護者による別端末からの閲覧が必要になった場合のみ、認証付きクラウド同期を別フェーズとして検討する。

### 16.3 ライブラリとデータのライセンス

- Hanzi Writer本体：MIT License
- `hanzi-writer-data-ja`：AnimCJK由来。Arphic Public Licenseの条件を確認して表示・同梱する
- KanjiVG：CC BY-SA 3.0。利用する場合はクレジットと継承条件を満たす
- 採用するデータのバージョンとライセンス文をリポジトリに固定し、CDNの最新版へ無条件に依存しない

### 16.4 Androidでの提供方式

初期版はAndroidネイティブアプリではなく、ChromeからインストールできるPWAとして作る。

- Web App Manifestの `display` を `standalone`、`orientation` を `landscape` にする
- Androidのホーム画面へ追加し、通常はブラウザのURLバーがないアプリ表示で使う
- Service Workerで画面、教材、必要な漢字データをキャッシュする
- IndexedDBに回答を即時保存し、通信が不安定でも回答を継続できるようにする
- Android版Chromeの1つの対応バージョンを決め、実機テスト対象を絞る

PWAを優先する理由は次のとおり。

- Reactのコードだけで開発・更新できる
- APK、署名鍵、Google Play公開、ストア審査が不要
- 静的ホスティングへ反映すれば、タブレット側で再インストールせず更新できる
- ホーム画面追加、横向き指定、オフライン利用が今回の要件に合う
- Hanzi WriterはWeb向けライブラリなので、そのまま組み込める

次の問題が実機検証で発生した場合のみ、同じReactアプリをCapacitorでAndroidアプリ化する。

- 指やペンの入力遅延が学習を妨げる
- 横向き指定が対象端末で安定しない
- オフラインキャッシュやストレージの保持が不安定
- 画面スリープ制御、ローカル通知、専用ファイル保存などのネイティブ機能が必要になる
- Google Playから配布する必要が生じる

このため、画面や学習ロジックをブラウザ固有APIへ密結合させず、将来Capacitorで包める構造にしておく。ただし、初期版にはCapacitorやAndroid Studioを導入しない。

## 21. 画面設計の進め方

画面設計は、最初から実装コードや静止画像を作り込まず、会話内で操作できる横向きタブレットのプロトタイプを使って検討する。

### 21.1 推奨ワークフロー

1. 主要画面の目的と遷移を短く決める
2. Xiaomi Pad 6の16:10画面に合わせ、1,440×900 CSS pxを仮基準とした操作可能なプロトタイプを作る
3. 50音表、手書きエリア、「分からない」、次の問題への遷移を実際に操作して確認する
4. 娘さんにも触ってもらい、文字サイズ、タップしやすさ、迷う箇所を記録する
5. 会話で修正指示を出し、同じプロトタイプを更新して比較する
6. 方向性が固まった後、必要ならFigmaへ画面・コンポーネント・状態を整理する
7. 承認した画面からReactコンポーネントとして実装する

### 21.2 ツールの使い分け

| ツール | 主な用途 | 今回の位置付け |
| --- | --- | --- |
| 会話内の操作可能プロトタイプ | 素早い比較、タップ動作、状態変化、親子での試用 | 最初に使用する |
| Figma | 画面遷移、コンポーネント、デザイン仕様、長期的な管理 | 方向性が固まった後の候補 |
| Canva | 色・雰囲気の検討、イラスト、背景、簡単な静止画 | 補助用途 |
| 実装中のPWA | 手書き精度、実機性能、オフラインなど本物の動作確認 | UI承認後 |

Canvaは見た目の方向性やイラスト作成には向いているが、50音表入力、書き順判定、未習チェック、エラーと再挑戦など、多数の状態を持つ操作検証の中心にはしない。Figmaは画面間の遷移やインタラクティブコンポーネントを整理する用途に適している。

### 21.3 最初に作るプロトタイプ

最初の対象は漢字の1問分に絞る。

- 読み問題：問題文、回答欄、ひらがな／カタカナ50音表、削除、回答

- 正解状態：短い肯定表示と次へ
- 不正解状態：再入力と短いヒント
- 分からない状態：書き順表示、なぞり書き、再挑戦

この1問の操作が固まってから、ホーム、漢字一覧、カスタム問題管理、学習記録へ広げる。

- 50音表を押し間違えないか
- 指やペンで書く領域が十分に大きいか
- 不正解時に責められた印象を与えないか
- 「分からない」を安心して押せるか
- 次へ進めない理由が明確か
- 1問に時間がかかりすぎないか
- 保護者向け操作を子どもが誤って変更しにくいか

## 23. 端末内保存・第1実装の安全設計

今回の対象はIndexedDBの初期スキーマと、学習回答を追記・読み出しする保存層までとする。JSONバックアップ復元、全削除、クラウド同期、画面上の保護者操作は対象外とする。

| 状態／操作 | 許可する結果 | 拒否または維持する結果 |
| --- | --- | --- |
| DBを初めて開く | 必要なストアと索引を1トランザクションで作る | 一部だけ作られた状態を利用しない |
| 新しい回答IDを保存 | 回答を1件追加する | 生の筆跡や筆圧は受け取らない |
| 同じ回答IDを再保存 | 既存回答を維持し、重複追加しない | 内容の異なる回答で上書きしない |
| 履修状態・設定を保存 | 同じキーの最新確定値へ更新する | 他ストアの回答履歴を変更しない |
| 読み出し中に失敗 | エラーとして呼び出し元へ返す | 空データとして成功扱いしない |
| 書き込み中に失敗 | トランザクション全体を失敗させる | 部分成功を完了として扱わない |

機械確認では、スキーマ作成、回答の追記、同一IDの冪等性、異なる内容による同一ID上書きの拒否、キー付き状態の更新、保存後の読み出しを検証する。実機では問題完了後に再読み込みしても回答が残ることを確認する。バックアップ復元と削除を実装する際は、別途データ置換の状態表と人による確認手順を追加する。

### 23.1 実装結果

- `attempts`、`kanjiStates`、`customQuestions`、`sessions`、`settings` の5ストアを作成

## 28. 出題順と苦手度（計画案）

出題モードは、保護者または学習者が開始時に次の2種類から選べる構成を第一候補とする。

| モード | 初期仕様 | 目的 |
| --- | --- | --- |
| 全問ランダム | 出題対象を一度シャッフルし、1周するまで同じ問題を重複させない | 全体を偏りなく復習する |
| 苦手順 | 苦手度の高い順。苦手度が同じ問題同士はランダムに並べる | 間違えやすい内容へ時間を集中する |

履歴として残す「累計ミス回数」と、出題順に使う「苦手度」は分ける。累計ミス回数は過去の事実なので減らさず、苦手度だけを正答実績によって増減させる。集計キーは問題IDではなく「漢字 × 読み／書き」とし、同じ漢字でも読みと書きは別能力として扱う。問題IDは、どの出題で記録されたかを追跡する履歴情報として残す。

### 28.1 漢字単位の収集方法

漢字ごとに、読みと書きそれぞれ次の値を持つ計画とする。

| 値 | 用途 |
| --- | --- |
| 対象漢字 | 集計の主キーとなる1文字 |
| 形式 | `reading` または `writing` |
| 出題回数 | その漢字を評価対象として出した回数 |
| 初回正解回数 | ヒントや誤答なしで正解した回数 |
| ミス出題回数 | 1回以上間違えた出題の回数 |
| 分からない回数 | 「分からない」を使った回数 |
| 累計書き間違い画数 | 書き問題だけで保持する詳細値 |
| 苦手度 | 出題順位に使う増減可能な値 |
| 最終出題日時・最終初回正解日時 | 長期間未復習の判定に使う |

書き問題は一文字ごとに書き順判定結果が得られるため、「植物」で「植」だけを間違えた場合は「植・writing」だけへミスを記録し、「物」へは加算しない。

読み問題は熟語をひとまとまりの読みとして評価する。正誤の原因を一文字へ分解せず、問題の `targetKanji` に含まれる全漢字を連帯責任とする。たとえば「植物＝しょくぶつ」を誤答した場合は「植・reading」と「物・reading」の両方へミスを記録し、初回正解なら両方の初回正解を記録する。同じ漢字が問題内に複数回現れても、1回の出題につき各漢字の更新は1回までとする。

### 28.2 苦手度の更新

苦手度の初期更新ルール案は次のとおり。

- 初回回答で正解し、見本も使わなかった：苦手度を1減らす（下限0）
- 1回でも誤答した、または「分からない」を使った：苦手度を1増やす
- 同じ出題内で何度間違えても苦手度の加算は1回までとし、詳細な誤答回数や書き間違い画数は履歴へ別に残す
- 間違えた後に正解しても、その出題では苦手度を減らさない。後日の出題で最初から正解できたときに減らす

書き問題は文字ごとの結果に応じて各漢字を個別更新し、読み問題は熟語に含まれる対象漢字をすべて同じ結果で更新する。苦手度の下限は0とし、上限は実装前に決める。

この方式なら、複雑で画数の多い漢字だけが過度に不利になることを防ぎながら、「以前は苦手だったが今は覚えた」という変化を表現できる。苦手順で未出題・苦手度0の問題が長期間出なくなる問題を避けるため、将来は苦手問題中心に一部の通常問題を混ぜる方式も検討する。初期実装では動作が説明しやすい厳密な苦手度順から始める。

苦手順で複数漢字を含む読み問題を並べる場合は、構成漢字の苦手度の最大値をその問題の順位として使う。どれか一文字でも苦手度が高ければ、その熟語を優先して復習する。平均値にすると他の得意な漢字によって苦手が薄まるため採用しない。

### 28.3 保存と更新の安全設計

回答履歴を正本とし、漢字単位の集計は再計算可能な派生データとして保存する。既存履歴を書き換えず、新しい回答が確定した時点で履歴追加と該当漢字の集計更新を同一トランザクションで行う。

| 状態／操作 | 許可する結果 | 拒否または維持する結果 |
| --- | --- | --- |
| 初回正解 | 対象漢字・形式の初回正解を加算し、苦手度を1減らす | 別の漢字や別形式を更新しない |
| 誤答後に正解 | ミス出題を1回加算し、苦手度を1増やす | 最終正解で同じ出題の加算を相殺しない |
| 「分からない」 | 分からないとミス出題を記録し、苦手度を1増やす | 見本表示だけして記録を省略しない |
| 複数字の書き問題 | 文字ごとの結果を各漢字へ反映する | 語句全体のミスを全漢字へ一律加算しない |
| 読み問題 | `targetKanji` の全漢字へ同じ正誤結果を1回ずつ反映する | 一部の漢字だけを推測で更新したり、同じ漢字へ重複加算したりしない |
| 保存の再試行 | 同じ回答IDなら二重加算しない | 履歴1件に対して集計を複数回更新しない |
| 集計更新失敗 | 履歴追加と集計更新をまとめて失敗させる | 履歴と集計が不一致の部分成功を残さない |

自動テストでは、読み／書きの分離、書きでは誤った文字だけを加算すること、読みでは対象熟語の全漢字を同じ結果で更新すること、同一漢字の重複加算防止、初回正解による下限0の減算、誤答後正解の非相殺、同一回答IDの冪等性、トランザクション失敗時の不変性、既存履歴からの再集計一致を確認する。スキーマ更新を実装する際は、既存の回答履歴と未習設定が保持されることを人による確認項目にも含める。

実装前に残る決定事項は、1回の学習で出す問題数、苦手度の上限、読みと書きの出題モードを個別に選ぶか共通にするか、学習途中で終了した場合の扱いである。既存の回答履歴は維持し、新しい漢字単位集計を追加するIndexedDB更新と移行テストは別工程で実施する。

## 29. 3・4年生漢字の問題生成計画

### 29.1 生成単位

3年生200字、4年生202字について、各漢字に存在する音読み・訓読みを1項目ずつ問題化する。生成キーは次の組み合わせとする。

`学年 × 主対象漢字 × 音訓区分 × 読み`

1文字に音読みが2つ、訓読みが1つある場合は、共通出題素材を3件作る。音読みまたは訓読みが存在しない漢字へ、存在しない区分の問題は無理に作らない。人名用だけの読みは対象外とし、常用漢字表に含まれる読みを基準にする。送り仮名が異なる訓読みは別項目として扱う。

例として、1つの漢字に次の読みがある場合は3素材となる。

| 主対象漢字 | 区分 | 基準となる読み | 使用語例 | 生成する形式 |
| --- | --- | --- | --- | --- |
| 仮の漢字 | 音 | 読みA | 語例A | 読み＋書き |
| 仮の漢字 | 音 | 読みB | 語例B | 読み＋書き |
| 仮の漢字 | 訓 | 読みC | 語例C | 読み＋書き |

### 29.2 読み・書きの共通素材

読み問題をそのまま書き問題へ変換できるよう、画面形式に依存しない共通素材を先に作る。共通素材は少なくとも次を持つ。

| 項目 | 内容 |
| --- | --- |
| `pairId` | 読み問題と書き問題を結ぶ不変ID |
| `grade` | 3年生または4年生 |
| `primaryKanji` | 今回の読みを網羅する主対象漢字 |
| `readingType` | 音読み／訓読み |
| `canonicalReading` | 読み一覧上の基準読み |
| `word` | 実際に出題する語句 |
| `wordReading` | 語句全体のひらがな読み |
| `promptBefore` / `promptAfter` | 読み問題の例文 |
| `targetKanji` | 語句に含まれ、読みで連帯責任となる漢字一覧 |
| `writingPrompt` | 書き問題で表示するかな中心の指示文 |
| `sourceRef` | 読み一覧・語例の根拠と版 |
| `reviewStatus` | 未確認／確認済み／要修正 |

この共通素材1件から、同じ `pairId` を持つ読み問題と書き問題を各1件生成する。読み問題では例文中の語句全体の読みを50音表で答え、書き問題では同じ語句を一字ずつ書く。学習履歴の形式は別々に記録するが、どの読みと書きが対になっているかを追跡できる。

音読み一覧ではカタカナ表記される場合も、児童が入力する `wordReading` はひらがなに統一する。連濁、促音化、長音相当の「う」など、語句の中で表面上の読みが変化する場合は、`canonicalReading` と実際の `wordReading` を分けて保持する。

### 29.3 語句・例文の生成条件

- 4年生が意味を理解しやすく、家庭学習で不自然でない語句を優先する
- 主対象の読みが、その語句の中で実際に使われていること
- 訓読みは必要な送り仮名まで含めて区別する
- 例文を読めば語句を推測できるが、答えそのものを表示しないこと
- 例文と語句の補助部分に表示できる漢字は、その問題の学年までに配当された漢字に限定する。3年生問題では1〜3年生、4年生問題では1〜4年生の漢字だけを使用し、それより上の学年で習う漢字は文中での読み方に合わせてひらがなにする
- 今回答えさせる `primaryKanji` と `targetKanji` は問題の対象なので表示制限によるひらがな化をしない
- 同音異義語は文脈で意味を区別できる例文にする
- 不自然な造語、固有名詞、人名・地名だけに依存する問題を避ける
- 同じ語句を複数の読み項目で使う場合も、各生成キーと主対象漢字を明示する
- 読み問題では語句内の `targetKanji` 全字を連帯責任で集計し、書き問題では一字ごとの判定結果を個別集計する

### 29.4 生成工程

1. 3・4年生402字と、その音訓読みを版付きの基準一覧へまとめる。
2. 各生成キーに対し、読みを実際に使う語句候補を作る。
3. 語句候補から児童向けの例文と書き指示を生成する。
4. 学年別漢字配当表を使い、対象漢字以外の上位学年漢字を文脈上の読みでひらがなへ変換する。
5. 共通素材から読み問題・書き問題のJSONを機械生成する。
6. 機械検査を通した後、日本語としての自然さ、読み、送り仮名、学年相当性を人が確認する。
7. `reviewStatus=確認済み` の問題だけを公開用問題パックへ含める。

生成は再実行可能なスクリプトにし、人が直した公開済みJSONを直接上書きしない。読み一覧と共通素材を入力データ、読み／書き問題パックを生成物として分離する。生成AIを語句・例文候補作成に使う場合も、自動公開はせず全件をレビュー対象とする。

### 29.5 機械検査と人による確認

機械検査では次を必須とする。

- 全402字が基準一覧に存在する
- 基準一覧の全音訓読みについて、共通素材がちょうど1件存在する
- `学年 × 主対象漢字 × 音訓区分 × 読み` の重複・欠落がない
- 各共通素材から読み問題と書き問題が1件ずつ生成される
- 対になる2問の `pairId`、語句、読み、対象漢字が一致する
- `primaryKanji` が `word` と `targetKanji` に含まれる
- 対象漢字を除き、3年生問題に4年生以上、4年生問題に5年生以上の配当漢字が残っていない
- ひらがな化した箇所が、熟語・活用・送り仮名を含めて文中での実際の読みと一致する
- 読み回答が現在のひらがな入力UIで入力できる文字だけから成る
- 問題IDと `pairId` が版をまたいでも不用意に変わらない
- 未確認問題が公開パックへ混入しない
- 生成件数と音読み・訓読み別のカバレッジ報告を出力する

上位学年漢字の変換は、文字単位の機械的な置換ではなく、語句中の表面読みを使う。たとえば音便、連濁、活用、送り仮名を考慮し、変換後の例文全体を保存する。自動変換に確信が持てない箇所は公開せず `要修正` とする。

人による確認では、語句で本当にその読みが使われるか、連濁などの変化が正しいか、上位学年漢字が残っていないか、ひらがな化した文が自然か、学年に不適切・難解な内容がないか、書き問題が読み問題と同じ知識を問えているかを確認する。全件一括確認が難しいため、学年・漢字・読み別にレビュー状況を保存し、中断・再開できる一覧を用意する。

### 29.6 問題更新時の扱い

語句や例文を修正しても、同じ読みを評価する限り `pairId` と問題IDは維持し、過去の漢字単位学習履歴を継続利用する。評価する読みや主対象漢字が変わる場合は新しいIDを発行する。旧問題を問題パックから外しても、過去の回答履歴と漢字別集計は削除しない。

実装前に、基準とする音訓読み一覧、常用漢字表で複数表記される読みの正規化方法、語句候補の初期作成方法、全件レビューの分担方法を確定する。基準一覧を確定した時点で、共通素材数と読み・書きそれぞれの最終問題数を自動集計する。
