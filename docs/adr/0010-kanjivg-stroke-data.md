# ADR-0010: ストロークデータを KanjiVG へ移す

- Status: Accepted
- Date: 2026-08-27

## Context

書き取りの正誤判定と見本表示は `@jamsch/hanzi-writer-data-jp` に依存している。このデータは animCJK と Make Me a Hanzi を経由した Arphic Technology のフォント由来である。

2026-08-27 に、糸偏の下3画を「左→中→右」の順で書くことを確認した。日本の標準は「中→左→右」（「小」の書き順）で、KanjiVG もそうなっている。収録済みでは級・給・終・線・緑・練の6字が該当する。単体の「糸」と「必」は KanjiVG と一致するため、データ全体が中国式なのではなく、糸偏という部品に限定した不具合である。

字形そのものは日本のものだった（海=9画など、画数は照合済み）。問題は**書き順**であり、アプリは誤った順を正解として判定していた。

既存データの並べ替えで直すことも検討したが、機械的な対応付けは級・終でしか成立せず、練・線・緑・給では破綻した（正規化距離 0.47〜0.60）。順序だけでなく下3画の**配置と形**も違うためで、並べ替えでは形が教科書と別物のまま残る。

[study-support-plan.md](../study-support-plan.md) 1章はこのアプリの目的を「苦手な内容を優先して復習できる」とし、266行は「日本語字形と書き順は公式資料・KanjiVG等を照合し、人による確認を必須とする」と定めている。照合先として名指しされているデータを、正本そのものに使う。

## Decision

- 書き順・字形の正本を **KanjiVG**（Ulrich Apel、CC BY-SA 3.0）とする。
- KanjiVG の SVG を `content-source/kanjivg/` へ取り込み、リポジトリに含める。ビルド時のネットワーク取得はしない（オフラインで `npm run content:generate` を再実行できるようにするため）。
- KanjiVG は中心線しか持たないため、生成時に中心線を等幅で太らせた閉じた輪郭を作る。`strokes` は生成した輪郭、`medians` は中心線の標本点とする。
- 線幅は 1024 座標系で **31**、標本点は 1画あたり **10点**とする。
- `@jamsch/hanzi-writer-data-jp` への依存は削除する。

生成物の扱いを固定する。

| 対象 | ライセンス | 理由 |
|---|---|---|
| リポジトリのコード | MIT | 自分の著作物 |
| `content-source/kanjivg/` | CC BY-SA 3.0 | KanjiVG そのもの |
| `src/generated/kanjiCharacterData.ts` | CC BY-SA 3.0 | KanjiVG の派生物 |

出典表示は [THIRD-PARTY-NOTICES.md](../../THIRD-PARTY-NOTICES.md) と、アプリ内の保護者設定から見える位置に置く。配信物（GitHub Pages の JavaScript）がデータを再配布するため、リポジトリ内の表記だけでは足りない。

## Consequences

- 糸偏6字の書き順が日本の標準になる。他の字も KanjiVG が正本になるため、全368字の書き順監査は不要になる。
- **見た目が変わる。** 線幅が均一になり、明朝系の太細の抑揚と筆の入り・払いが失われる。368字すべての表示が変わるため、人による確認が要る。
- 配信サイズが増える。実測で、10点/画・整数座標なら368字で約1,240KB（現行1,122KB、+11%）。標本点を増やすほど曲線は滑らかになるがサイズも増える。ビルドは既に500KB警告が出ているため悪化する。
- CC BY-SA 3.0 の継承条件が生成物に付く。派生物を再配布する第三者にも同じ条件がかかる。
- 曲線の多い字が10点/画でどこまで滑らかかは未検証で、実機確認で判断する。滑らかさが足りなければ点数を増やし、サイズと引き換える。
