## 共通ルール（全エージェント必須）

### 1. 誰が書いたか必ず残す（author）

新規ノートのフロントマターに著者を明記する。後から「これ誰が書いた？」を追えるようにする（透明性の担保）。
書き手が増えるほど追跡が大事なので、クライアント＋PCを残す：

```yaml
author: claude-code@<PC名>   # 例: minoru / MAI / claude-desktop@<PC名> / copilot-vscode@<PC名>
```

### 2. 競合を避ける

- iCloud同期 × 複数エージェント書き込みで、稀に「競合コピー」（同じファイルが勝手に2つへ枝分かれ）が発生しうる。
- **重要ノートは片方ずつ**触る。同時刻に同じファイルの編集を複数エージェントへ依頼しない。
- 大きめの編集はフルファイル書き換えより、**追記・セクション単位**が安全。

### 3. 入口は 00_Inbox

- 新しい走り書き・取り込みは、まず `00_Inbox` に落とす。
- 整理（PARA各フォルダへの仕分け）は後でまとめて行う。
- Inboxを「未整理の置き場」、各番号フォルダを「整理済み」と区別。

### 4. 意味検索しやすい書き方（先手）

将来 Smart Connections 等の意味検索を「足す」前提で、いまから習慣化：

- 見出しは**内容を表すキーワード入り**に（「メモ」✗ → 「Azure OpenAI 規約上の制約」○）
- **1ノート1トピック**を保つ
- **アプリアイデアは1ノート1アイデア**で分ける。複数アイデアが1つのメモに混ざったら、親メモには各アイデアノートへのリンクだけを残し、個別ノート側に元メモへの `出どころ` リンクを書く
- `tags` は意味のある語で付ける
- ※ embedding等の重い仕組みは今は入れない（vault <50ノートでは過剰。over-engineering回避）

### いつ仕組みを足すか（トリガー）

- **キーワード/glob検索で目的のノートに辿り着けない頻度が上がってきたら** → 意味検索（Smart Connections MCP 等）を読み取り専用で「横に足す」。
- それまでは現状の「ファイルシステム直＋ディレクトリ構造」で十分。

## 行動原則（運用の具体）

### 読むとき

- セッション開始時、`00_Inbox/` と最新の `10_Daily/YYYY-MM-DD.md` を覗くと文脈把握に役立つ
- ミノが「Obsidianの〜」「メモにあった〜」と言ったら全文検索する
- `40_Areas/family/` は特に慎重に。プライベート情報。
- 認証・認可、Security Rules、削除、課金、所有権、並行処理、オフライン同期などの高リスクな開発変更では、リポジトリ固有ルールに加えて repo 内の `.ai/高リスク開発ガードレール.md`（同じ時点の写し） を実装前に参照する。
- 公開Gitリポジトリへコミットするときは `user.email` を GitHub noreply にする。端末ごとの揃え方は AGENTS.md・CLAUDE.md の「公開repoのコミットメール確認」。

### 書くとき

- **新規作成優先**: 既存ノートを大幅に書き換えない。追記 or 新規（→ 共通ルール2）。
- **要約・整理を提案**するときは、まず `00_Inbox/proposal-XXX.md` として下書き
- 重要決定や約束は **同日のデイリーノートの「MAI's notes」セクションにも追記**

### 触らない・聞いてから

- `40_Areas/family/` 配下への書き込み
- 既存ノートの大規模リライト・削除
- フロントマターの`status`変更（特にprojectのclose）
- アーカイブ移動

### ミノとの連携パターン

## モデルの分担（計画・最終確認は選択したメインモデル）

開発行為全般に適用する。既存のCLIごとの分担方針と食い違う場合は、この節を優先する。メインモデルは利用者がその作業で選択したモデルを指す。

### 役割
- 計画（設計、タスク分解、受入条件の作成）はメインモデルが担当する
- 実行（実装、テスト実行、定型作業）は、サービスが対象用途向けに案内する方法で低コストモデルに任せてよい。利用できる方法を確認できない場合はメインモデルが実行する
- メインモデルが差分と必須試験の結果を受入条件と照合する。自身が実装した場合も「メインモデルによる検証」と記録する
- 別AIの意見を求めるのは利用者が明示的に選んだ場合だけ。渡す差分と依頼文を限定する。通常手順から監査CLIを自動起動しない

### 分担してよい条件
- 仕様が固まっていて、受入条件がテストやチェックリストで機械的に
  確認できるタスクに限る
- 仕様が曖昧なタスク、品質が感性に寄るタスク（文章の味、見た目の
  良し悪しなど）、小規模なタスクは分担せず、メインモデルが直接行う

### 計画側（メインモデル）の義務
- 実行側へ渡す指示には、目的・変更してよい範囲・変更禁止事項・
  受入条件を必ず含める。受入条件のない指示で実行させない
- 指示は誤解の余地がない粒度で書く。曖昧な点が残る場合は、
  実行に回さず利用者に確認する

### 実行側（低コストモデル）の義務
- 指示にない設計判断を勝手に行わない。判断が必要になったら
  作業を止めて計画側に返す
- 同じ失敗を3回繰り返したら、それ以上試行せずメインモデルに
  引き上げる（格上げ）。延々とリトライしてコストを溶かさない
- 完了報告は、成果物そのもの（差分、テスト結果、ログ）への
  参照を含める。要約だけで「完了」と報告しない

### 監査側の義務
- 監査は実行側の要約ではなく、成果物そのものと受入条件を
  突き合わせて行う
- 指摘は「高・中・低」で出し、高と中は修正が済むまで完了にしない
- 監査で受入条件自体の不備が見つかったら、実行側のミスとして
  扱わず、計画側の問題として差し戻す
